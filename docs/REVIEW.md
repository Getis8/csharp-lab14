# Крос-рев'ю, лабораторна №14 (поведінкові шаблони: Observer, Mediator)

Розподіл: Катя реалізувала Завдання 1 (Observer), Стас реалізував Завдання 2 (Mediator).
Рецензенти: Стас перевіряє Завдання 1, Катя перевіряє Завдання 2.

Критерії (з умови): діаграма відповідає коду; рішення усуває проблему з опису; раннер відтворює демонстраційний сценарій; для кожної ситуації в журналі видно, хто ініціював подію і хто на неї відреагував.

## Завдання 1. Observer (рецензент: Стас)

| Критерій | Що перевірено | Результат |
|---|---|---|
| Діаграма відповідає коду | `ICarEventObserver` (Observer), `Car` (Subject) зі списком `_observers`, методами `Subscribe`, `Unsubscribe`, `Publish`, чотири конкретні підписники, `CarEvent` | ☐ |
| Рішення усуває проблему | `Car` не знає конкретних отримувачів, лише інтерфейс; страхова підключається без змін у `Car`; підписка і відписка під час виконання; кожен підписник у `OnCarEvent` сам вирішує, на які події реагувати | ☐ |
| Раннер відтворює сценарій | Клієнт підписується на час поїздки; заряд 10%: реагують клієнт і служба обслуговування; удар: диспетчер і страхова; поїздка завершується, клієнт відписується | ☐ |
| Видно ініціатора і реакцію | Рядок `[Авто CE1234AA] ініціює подію ... підписників: N`, далі рядки кожного підписника від його імені | ☐ |
| Контрольна перевірка | Після відписки клієнта подія заряду 5% доходить лише до служби обслуговування | ☐ |

| № | Зауваження | Статус |
|---|---|---|
| 1 | `Publish` розсилає по копії списку (`ToList()`), тому відписка під час розсилки не ламає ітерацію | ☐ прийнято |
| 2 | `Subscribe` ігнорує повторну підписку того самого об'єкта, дублікатів немає | ☐ прийнято |
| 3 | `Car` не потокобезпечний (звичайний `List`); для консольного демо прийнятно, у захисті згадати `lock` або `ImmutableList` | ☐ прийнято |
| 4 | Порядок реакцій залежить від порядку підписки; для цієї задачі він не важливий, але це відомий мінус Observer | ☐ прийнято |

## Завдання 2. Mediator (рецензент: Катя)

| Критерій | Що перевірено | Результат |
|---|---|---|
| Діаграма відповідає коду | `IDispatchMediator` (Mediator), `DispatchCenter` (Concrete Mediator), `DispatchService` (Colleague), п'ять служб і `CarWashService` | ☐ |
| Рішення усуває проблему | Служби знають лише посередника, а не одна одну; усі правила реагування в `DispatchCenter.Notify`; мийка підключається без змін в існуючих службах | ☐ |
| Раннер відтворює сценарій | Завершення ремонту: авто повертається на карту; ДТП: завершення поїздки, виклик евакуатора, прибирання з карти, звернення підтримці; після підключення мийки авто йде на мийку | ☐ |
| Видно ініціатора і реакцію | `[Служба] ініціює подію`, `[Координатор] Отримав ... від «...»`, далі дії служб від їхнього імені | ☐ |

| № | Зауваження | Статус |
|---|---|---|
| 1 | `DispatchCenter` може розростися в «божественний об'єкт» при багатьох службах; для п'яти службу це прийнятно, у захисті назвати це мінусом Mediator | ☐ прийнято |
| 2 | Підключення мийки змінює лише координатор (`ConnectCarWash`, нове правило), існуючі служби не чіпаються: це відповідає вимозі | ☐ прийнято |
| 3 | `Mediator` у службі має `internal set`, тому призначити посередника ззовні збірки не можна | ☐ прийнято |
| 4 | `Notify` використовує `switch` за типом події: це правила координатора, а не розгалуження за типом служби | ☐ прийнято |

## Підсумок

Діаграми відповідають коду, вимоги з описів ситуацій виконано, раннери відтворюють сценарії, у журналі видно, хто ініціював подію і хто відреагував. До захисту: підготувати відповіді на питання про різницю Observer / Mediator (Observer: один розсилає багатьом, не знаючи їх; Mediator: багато спілкуються через одного, правила в ньому).
